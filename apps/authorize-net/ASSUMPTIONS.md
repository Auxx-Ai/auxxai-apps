# Authorize.net app — assumptions

Build plan §9 phase 0 (the live probe) has not run: no org holds an Authorize.net
credential. Everything below is read from the vendor reference or inferred, and every
row is something the probe must confirm before this app is trusted with real money.

| # | Assumption | Where in code | What the probe must confirm |
| --- | --- | --- | --- |
| 1 | The response body carries a leading UTF-8 BOM. | `tools/shared/authorize-net-api.ts` `stripBom` | Whether the BOM is there. Stripping one that is absent is harmless, so this is safe either way. |
| 2 | HTTP status is 200 even on failure; the real outcome is `messages.resultCode`. | `authorize-net-api.ts` | That a transport-level 4xx never carries a usable `messages` block. |
| 3 | `E00007` / `E00008` mean "bad or expired credential" and `E00011` means "access denied" (the Transaction Details API toggle). | `authorize-net-api.ts` `AUTH_ERROR_CODES`, `PERMISSION_ERROR_CODES` | The code actually returned when the reporting toggle is off. Everything else surfaces as `AuthorizeNetApiError` with its code, so a miss is visible, not silent. |
| 4 | There is no `resultCode`-level throttle; a throttle arrives as HTTP 429, possibly with `Retry-After`. | `authorize-net-api.ts`, connector `rateLimited` | The real rate-limit signal. If it is a result code, add it to the mapping. |
| 5 | Some surfaces wrap the payload in `<name>Response`, some return it bare. | `authorize-net-api.ts` `unwrap` | Which one this account gets. Both are handled. |
| 6 | `getSettledBatchList` caps its range at 31 days. | `settlements.ts` `AUTHORIZE_NET_MAX_WINDOW_DAYS`, connector window walk | The real cap. A smaller real cap means silently truncated windows, so this is the highest-risk row here. |
| 7 | `paging.offset` is 1-based and `totalNumInResultSet` is reliable. | `settlements.ts` `fetchBatchTransactions`, connector `fetchMemberPage` | Both. The loop also terminates on a short page, so an unreliable total degrades to "one page" rather than to a loop. |
| 8 | `transactions` may be `[...]` or `{ transaction: [...] }`, and `totalNumInResultSet` may be a string or a number. | `settlements.ts` `asArray`, `asCount` | Which serialization this account returns. |
| 9 | The LIST row carries `settleAmount`. | `settlement-evidence.ts` `processorEvidence` (falls back to `amount`, then `authAmount`) | That it does. If it does not, membership needs one `getTransactionDetails` per transaction — 6,000+ calls for history, and a different design. |
| 10 | The LIST row names **no** `transactionType`, so the activity kind is read from `transactionStatus` alone there. | `authorizeNetActivityKind(undefined, status)` | Whether a type is present after all. The detail surface is handled the documented way. |
| 11 | The invoice field is `invoiceNumber` on some surfaces and `invoice` on others; either is `sourceOrderId` VERBATIM. | `processorEvidence` | The real key, and whether Shopify puts the order name in it (build plan §6 B). |
| 12 | `refundSettledSuccessfully` is the status of a settled refund in a batch. | `SETTLED_STATUSES`, `authorizeNetActivityKind` | The status string a refund actually carries. |
| 13 | A refund's / returned item's `settleAmount` is reported UNSIGNED, so the app signs it negative. | `processorEvidence`, `OUTGOING_STATUSES` | The sign the gateway uses. An already-negative value is left alone, so a double negation cannot happen — but an unsigned chargeback reversal would be mis-signed. |
| 14 | `...UTC` timestamps may arrive without a `Z` (the reference's own example does). A naked one is stamped UTC. | `evidenceTimestamp` | Whether the `Z` is there. The contract requires an offset, so a naked value would otherwise be rejected outright. |
| 15 | The header amount is Σ over `statistics[accountType]` of `chargeAmount − refundAmount`, less `returnedItemAmount` on eCheck rows. `chargebackAmount` is deliberately NOT subtracted. | `batchNetMinor` | Whether the header agrees with Σ members on a batch with refunds, with a returned eCheck, and with a chargeback. A chargeback that is also a member row will show a difference — that is the intended visible outcome, not a bug. |
| 16 | A chargeback / returned item is a MEMBER row, not only a statistic. | `ADJUSTMENT_STATUSES` | If it is only a statistic, membership will be short by that amount and `assessPayoutMembership` will refuse the batch — correct, and visible. |
| 17 | `settlementState !== 'settledSuccessfully'` still produces a header, carrying that state as `status` and `providerReady: false`, so the platform's own assessment refuses it. The batch is never dropped. | `payoutEvidence`, connector `payoutRecord` | Which states occur, and whether a `settlementError` batch carries money. |
| 18 | `getMerchantDetails` returns `gatewayId` and `currencies`. If the call fails or names neither, the account identity is the API Login ID and the currency is USD. | `resolveAccount`, `AUTHORIZE_NET_DEFAULT_CURRENCY` | That `gatewayId` exists and is stable. `connection-identify` uses the API Login ID unconditionally, because it is pre-insert and must make no provider call. |
| 19 | The member page size is **250**, not the gateway's 1000: `payoutRecordEvidenceSchema` caps a persisted membership page at 250 entries and 250 raw rows. | `AUTHORIZE_NET_MEMBER_PAGE_LIMIT` (the gateway cap stays as `AUTHORIZE_NET_PAGE_LIMIT`) | Nothing at the provider — this is a platform constraint, stated here because the contract this app was written against named 1000. |
| 20 | The `balance_transaction` stream is DROPPED (build plan §8 / §10.5). Nothing in the platform requires a connector to declare a root `processor_balance_entry` stream — `assertLegacyPayoutIngestionOwner` no longer exists in the platform worktree, and no catalog validation was found that demands one. | `authorize-net.connector.ts` (one stream) | That the payout stream's fan-out to `processor_balance_entry` is enough for Payouts and Settlements. Unsettled transactions stay a read tool. |
| 21 | `buildPayoutEntry` is NOT reachable from these tests (it pulls `@auxx/lib/errors` and the ledger builders). The zero-fee claim is proved two other ways: the evidence envelope validates with `fee: "0.00"`, and the platform's own `splitStoredEntries` returns `feesMinor: 0`. | `tests/settlement-evidence.test.ts` | That `buildPayoutEntry` accepts `feesMinor: 0` on a `billed` rail. Its own docblock says `gross === net` is the expected arithmetic there, so this is very likely already true. |
| 22 | Every fixture in both test files is SYNTHETIC — shapes and vocabulary from the vendor reference, magnitudes invented. | `tests/*` | Replace with real probe payloads once phase 0 runs. |
